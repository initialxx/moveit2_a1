# 机械臂接入 MoveIt 2：两种适配方案对比

> **文档性质**：技术选型决策文档
> **阅读时间**：约 5 分钟
> **技术细节备查**：见 `onero-moveit2-adapter-comparison-techappendix.md`

---

## 一、背景：为什么需要一个「适配层」

**MoveIt 2 只负责"规划走什么轨迹"，不负责"怎么驱动电机"。**

它是一个运动规划框架——会算运动学、会做碰撞检测、会规划无碰撞路径。但它**完全不知道**我们的机械臂怎么通信、用什么协议、怎么发 CAN 帧。

所以需要一层代码，把 MoveIt 规划出的轨迹，变成我们机械臂能执行的动作。**这就是"适配层"。**

```
                    ┌──────────────────────────┐
   MoveIt 规划 ─────▶│      适 配 层            │─────▶ 机械臂
   （一条轨迹）       │ （把轨迹变成电机指令）    │
                    └──────────────────────────┘
                                  ↑
                     这就是我们要写的东西
```

**好消息是**：MoveIt 与适配层之间的接口是**固定**的（一个标准的"轨迹执行"接口）。
所以问题就简化为——**这个适配层怎么写**。有两种做法。

---

## 二、两种方案

```
方案 A：自写 action server
  MoveIt ──▶ ┌────────────────────┐
             │  我们的 Python 节点  │──▶ 机械臂
             │  轨迹执行 + CAN 通信 │
             └────────────────────┘

方案 B：ros2_control + 话题桥
  MoveIt ──▶ ┌──────────────┐  ┌──────────────┐
             │ ROS 现成框架  │─▶│ 我们的转发节点 │──▶ 机械臂
             │ （不用写）    │  │ （几十行）     │
             └──────────────┘  └──────────────┘
```

**通俗理解**：
- **方案 A** = 自己从头搭一个执行器
- **方案 B** = 用 ROS 现成的框架，自己只写一个"转发器"

---

## 三、核心对比

| 对比项 | 方案 A：自写 action server | 方案 B：ros2_control + 话题桥 |
|---|---|---|
| **开发量** | 大 | **小** ✅ |
| **谁控制机械臂** | 我们的节点 | ROS 框架 |
| **轨迹执行的细节** | 全部自己实现 | **ROS 框架现成提供** ✅ |
| **实时性** | **好** ✅ | 每周期多 2 次跨进程通信 |
| **SDK 能力完整发挥** | **不受限** ✅ | 只能走位置/速度/力矩 |
| **ROS 生态工具** | 用不上 | **完整可用** ✅ |
| **行业主流度** | 少数派 | **主流** ✅ |
| **依赖复杂度** | 低（只需 ROS 基础库） | 需要额外装 ros2_control |

---

## 四、三个关键差异

### 差异 1：开发量 —— 方案 B 省掉一大块工作

MoveIt 发过来的是一条**带时间戳的轨迹**。要正确执行它，需要处理不少细节：

- 按时间插值，算出每个控制周期该在哪
- 判断有没有走到位、走偏了要不要中止
- 用户中途按"停止"时平滑减速
- 持续上报执行进度
- 成功/失败要如实反馈（**报错了 MoveIt 才知道**）

**方案 B 里这些全部由 ROS 现成组件完成**，我们只写一个"订阅命令 → 转给 SDK"的节点。
**方案 A 里这些都要自己实现**，而且这些细节不亲手写一遍是想不全的（边界情况很多）。

> **这是方案 B 最大的优势**，也是多数厂商选它的真实原因——不是"更标准"，而是**少写代码、少踩坑**。

### 差异 2：能力边界 —— 方案 A 能让 SDK 的本事全部发挥

方案 B 的标准通道**只能传位置、速度、力矩**这三种量。

我们 SDK 里的这些能力，在这个通道里**没有位置**：

| SDK 能力 | 方案 B 下的处境 |
|---|---|
| 力控（`force_mode`） | 要另外开接口 |
| 拖动示教（`freedrive`） | 要另外开接口 |
| 负载辨识、碰撞检测、夹爪 | 要另外开接口 |
| 快速点对点运动（`movej` 等） | 需要另行设计互斥策略 |

能用，但它们是**挂在框架旁边**的，不在框架之内。每加一个能力都要重新处理一次。

方案 A 没有这个限制，因为接口完全由我们自己定义。

> ⚠️ **一个容易误会的点**：kp/kd（控制刚度/阻尼的参数）**两个方案都要另外传**。
> 因为 MoveIt 的协议里根本没有"增益"这个字段——这是 MoveIt 的设计，与 ros2_control 无关。
> **所以这一项不构成两个方案的差异。**

### 差异 3：实时性 —— 方案 A 更好，但可能不是瓶颈

方案 B 每个控制周期要跨进程传两次消息（命令下行、状态上行），会引入额外延迟和抖动。
方案 A 的轨迹是一次性送达的，控制循环在自己进程里，没有这个开销。

**但必须放在整体里看**：

```
方案 B 额外增加：  约 0.3 – 2 ms（估算，需实测）
我们 SDK 的 CAN 通信本来就有：  1 – 3 ms
```

> **方案 B 多出来的开销和 CAN 是同一量级，不是压倒性的。**
> 真正的瓶颈在 CAN 和 Python，不在这一层。

**结论**：对常规的位置控制，方案 B 的实时性损失**可以接受**。
只有做**高速遥操作**或**高频力控**时，才会成为问题。

---

## 五、两个方案的共同点（省得纠结）

以下几点**完全相同**，不构成选择依据：

| 共同点 | 说明 |
|---|---|
| **描述层工作** | URDF、运动学配置、关节限位等**一行都不用改**。选择只影响执行层 |
| **硬件调用方式** | 最终都是调用 SDK 的逐周期命令接口 |
| **kp/kd 的传递** | 都要另外开通道（见差异 2 的说明） |
| **可以后续切换** | MoveIt 只认那一个固定接口，换执行层**不用动配置** |

> **最后一条很重要**：这个选择**不是不可逆的**。可以先用成本低的一条跑通，将来根据实际需求再换。

## 六、怎么选

**只需回答一个问题：**

> ### 我们的机械臂是「一个执行位置指令的机构」，还是「有力控、示教、感知的完整平台」？
>
> - **前者** → 选**方案 B**（省事、标准、够用）
> - **后者** → 选**方案 A**（SDK 能力不受限，架构也更顺）

**辅助判断**：

| 如果…… | 选 |
|---|---|
| 团队没有精力实现并测试轨迹执行逻辑 | 方案 B |
| 希望 ROS 生态工具即插即用 | 方案 B |
| 需要把力控 / 示教 / 感知作为产品卖点 | 方案 A |
| 需要高速遥操作或高频力控 | 方案 A |
| 想先快速验证、后续再优化 | 方案 B（可逆） |

## 七、关于「合入 MoveIt 2 官方」

### 需要先纠正一个前提

**厂商驱动不会、也不需要合入 moveit2 仓库。**

MoveIt 2 是**平台**，我们的驱动是**插件**。打个比方：没有人会问"我的 Chrome 插件怎么合入 Chromium"——MoveIt 2 的机器人驱动是同一回事。

**事实依据**：

- UR、Franka、Kinova、xArm 等 **126 个官方列出的机器人，驱动全部在各自厂商的仓库里**
- MoveIt 2 仓库里**一个厂商驱动都没有**，全是通用算法
- 连 MoveIt 自己的参考机器人都放在独立仓库

### "接入官方"的真实形式：三条通道

| # | 通道 | 做法 | 最终效果 | 优先级 |
|---|---|---|---|---|
| 1 | **rosdistro 发布** | 用 bloom 把包发布到 ROS 官方源 | 用户 `sudo apt install`，进入官方包索引 | ★★★ **最实质** |
| 2 | **官方机器人列表** | 向 `moveit.ros.org` 提 PR | 出现在 MoveIt 官网机器人列表 | ★★★ **最直接** |
| 3 | moveit2 代码贡献 | 提**通用**的 bug 修复/改进 | 代码进入 MoveIt 2 本体 | ★★ |

**参照物**：Kinova Gen3（同样是 7-DOF）在 ROS 官方源里的包结构，和我们需要的几乎一样：

```
kortex_description   →  onero_a1_description   （机器人模型）
kortex_driver        →  onero_a1_driver        （驱动/适配层）
kortex_bringup       →  onero_a1_bringup       （启动配置）
*_moveit_config      →  onero_a1_moveit_config （MoveIt 配置）
```

**要点**：

- **两个方案在这件事上完全相同**，都不需要修改 moveit2 一行代码
- **通道 1 和 2 要求驱动仓库公开可用** → 涉及开源许可决策，需提前确认
- 通道 3 必须是**通用**问题（对所有人都适用），不能是"为了让我们的机械臂跑起来"

## 八、建议的下一步

| 步骤 | 内容 | 说明 |
|---|---|---|
| **1** | **先做描述层**：机器人模型 + 配置 + 用假数据跑通 MoveIt | **两个方案都必须做，不涉及选型** |
| **2** | 实测方案 B 的实际延迟（约 30 分钟） | **用数据而非估算做决策** |
| **3** | 确认开源许可与仓库可见性 | rosdistro 发布的前置条件 |
| **4** | 再定方案 A / B | 此时已有实测数据支撑 |

> **原则：不要让选型阻塞描述层的工作。** 描述层是共同前提，先做起来。
