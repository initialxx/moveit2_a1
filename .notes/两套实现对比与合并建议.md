# 两套实现对比与合并建议

> 对象：`armsdk/ros2/`（SDK 仓库内）与 `moveit2_ws/src/`（本工作区）
> 路径更新（2026-10-15）：原 `.onero_ws/` 内容已移到仓库根目录；下文的历史实现比较仍以 `.onero_ws` 称呼该方案。
> 目的：判定两者的关系、取舍与合并动作
> 结论基于**实测**，每条关键判断附证据与复现方法（见第八节）

---

## 〇、TL;DR

**这不是"两个可选方案"，而是同一个目标的先后两次尝试，且第二次绕过了第一次放弃的那个限制。**

| | `armsdk/ros2` | `.onero_ws` |
|---|---|---|
| 时间 | 2026-06 | 2026-10 |
| 形态 | standalone Python action server | 话题桥 + ros2_control |
| 放弃 ros2_control 的原因 | 「pluginlib 不支持 Python 插件」 | —— |
| ROS 2 路径是否跑通 | ❌ **从未跑通过**（两个独立阻断点，实测） | ✅ 端到端已验收 |
| 建议 | 保留为**参考**，移植 3 个价值点 | **作为骨架** |

**一句话**：`armsdk/ros2` 那次放弃 ros2_control 的理由是真的，但**那个限制并不是死路** —— 本工作区用「官方 C++ 话题插件 + Python 话题节点」绕开了它。

## 一、两者的来历

### 1.1 `armsdk/ros2`（2026-06-27）

git log 里那笔提交把来龙去脉写得很清楚：

```
79d416e 重构 ROS2 集成：改用 standalone node 方案

Code review 发现 ros2_control 的 pluginlib 不支持 Python 插件，
改为 standalone node 方案：
- 新增 arm_node.py: 200Hz 控制循环 + FollowJointTrajectory action
- 删除 hardware_interface.py: 无法在 Jazzy 中作为 plugin 加载
- 删除 controllers.yaml: 不再需要 ros2_control controller_manager
```

即：**先写了 `hardware_interface.py`（ros2_control 插件），发现 Python 写不了，于是整个推翻，自写 action server。**

### 1.2 `.onero_ws`（2026-10）

本工作区在重新调研上游政策后建立，选了话题桥路线。

### 1.3 关键判断：那个限制是真的，但不是死路

**「pluginlib 只支持 C++ 插件」—— 事实正确。** 但 `.onero_ws` **不写插件**，它用的是 ros-controls 官方提供的 **C++ 插件**，Python 只做话题层：

```
$ cat overlay/share/joint_state_topic_hardware_interface/*.xml
  <class name="joint_state_topic_hardware_interface/JointStateTopicSystem"
         type="joint_state_topic_hardware_interface::JointStateTopicSystem"
         base_class_type="hardware_interface::SystemInterface">
$ ls overlay/lib/
  libjoint_state_topic_hardware_interface.so        ← C++ 插件，官方提供
```

于是：
- ros2_control 生态的好处（`joint_trajectory_controller` 负责插值/容差/取消/反馈）**拿到了**
- Python 写的自由度**也保住了**
- **一行 C++ 都不用写**

> **这是整个对比里最重要的一点**：`armsdk/ros2` 当初撞的墙，是「用 Python 写 ros2_control 插件」这堵墙；
> 而话题桥根本不走那扇门。

| **文档** | 两个 README | 主 README + 检查清单 + 3 份选型文档 |
| **代码量** | ~700 行 | 3 包 + 6000 行（含文档） |

## 三、`armsdk/ros2` 的实测缺陷

> 严重度排序。**S1–S2 是实测跑出来的，其余来自代码审计 + 子代理 FK 实测。**

### 🔴 S1｜MoveIt 启动脚本有两个**独立的**致命阻断点，从未跑通

**实测**：`ros2 launch onero_moveit_config move_group.launch.py` 在本环境（Jazzy）**无法启动**。
分步实验（`tools/exp_armsdk_stepwise.sh`）显示是两层叠加：

**阻断点 1 —— SRDF 注释里的一个冒号**

```
[ERROR] [launch]: Caught exception in launch: Unable to parse the value of
parameter robot_description_semantic as yaml.
```

`move_group.launch.py:35-37` 用 `Command(["cat ", srdf_file])` 把 SRDF 内容作为参数值。
launch_ros 会对它做 `yaml.safe_load` 试探 —— 而 `a1.srdf` 里有两行含 `": "`：

```
 8: <!-- Planning group: full arm chain -->      ← 就是这两个冒号
34: <!-- Virtual joint: fixed to world -->
```

对照实测：xacro 生成的 URDF **没有** `": "`，所以 `yaml.safe_load` 成功（返回 str）侥幸通过；
SRDF 有，于是 launch 直接中止。

**阻断点 2 —— YAML 文件缺 `ros__parameters` 包裹**

把上面两个冒号去掉后（补丁打在副本上，未改原仓库），暴露下一层：

```
[move_group-1] what(): failed to parse arguments: Couldn't parse params file:
  '.../config/kinematics.yaml'. Error: Cannot have a value before ros__parameters at line 2
[rviz2-2] terminate called ... 同上
```

`move_group.launch.py:52-60` 把 YAML **文件路径**直接塞进 `parameters=[...]`，
launch_ros 转成 `--params-file`，而 MoveIt 风格的 YAML（顶层是 `arm:` / `joint_limits:`）
没有 `/**/ros__parameters:` 包裹 → rcl 解析失败 → **move_group 与 rviz2 双双崩溃**。

> 四份 YAML（kinematics / ompl_planning / joint_limits / moveit_controllers）**一个都没进节点**。
> 正确形态由 `MoveItConfigsBuilder` 自动生成：`robot_description_kinematics: <kinematics>`、
> `robot_description_planning: <joint_limits>`、`ompl: <ompl_planning>` 等。

**结论**：`armsdk/ros2` 的 MoveIt 配置链**从未被真正验证过**。

---

### 🔴 S2｜容差违规仍返回 SUCCESSFUL（安全相关）

`arm_node.py:339-345`：

```python
if max_error < 0.1:
    goal_handle.succeed()
    result.error_code = FollowJointTrajectory.Result.SUCCESSFUL
else:
    self.get_logger().warn(f"Trajectory goal tolerance exceeded: {max_error:.3f} rad")
    goal_handle.succeed()                                    # ← 仍然 succeed
    result.error_code = FollowJointTrajectory.Result.SUCCESSFUL   # ← 仍然 SUCCESSFUL
```

`GOAL_TOLERANCE_VIOLATED` 是**死代码**。机械臂偏离 0.5 rad，MoveIt 仍认为执行成功。
另外 goal 里的 `path_tolerance` / `goal_tolerance` **完全没被读取**，硬编码 0.1 rad。

---

### 🟠 S3｜整个 SDK 安全层被绕过

`arm_node.py:121` 直接 `new CanBackend(...)`。而 SDK 的 `Arm` 会包一层
`SafeBackend(inner, SafetyMonitor)`，提供：

- 位置限位钳制 · `max_delta_per_step=0.03 rad/步` 速率限制 · 力矩钳制
- 急停门 · NaN → 上次好值替换 · 跟踪误差看门狗

**这些在 ROS 2 路径下全部不生效。** 且 URDF 里 `velocity="30.0"` 是 SolidWorks 占位符
（真机上限 3–6 rad/s），ROS 2 侧没有 SDK 那种 `min(urdf, 硬件标定)` 兜底。

---

### 🟠 S4｜控制线程可静默死亡

`arm_node.py:166` 的 `_update_trajectory_command()` **没有 try 保护**，
而 `:281-297` 从不校验轨迹点 `positions` 长度 → 一旦长度不足，`:248-250` 抛 `IndexError`
→ **控制线程死掉**：臂再也收不到命令、`/joint_states` 冻结、action 永不返回、无任何日志。

---

### 🟠 S5｜失联不可见

`CanBackend` 支持 `on_miss` / `on_fault` 回调，但 `arm_node.py:121-125` **一个都没传**。
后果：掉帧时 SDK 复用上一次状态，`/joint_states` **无限期发布冻结的旧值**且无任何 ROS 侧错误指示；
SDK 自带的 `timeout_frames=10`（10 帧丢失即急停）在 ROS 2 路径下完全失效。

> 对比：`.onero_ws` 专门写了 `health_watchdog` 来堵这个洞（因为硬件插件不校验时间戳）。

---

### 🟠 S6｜正常退出即掉臂

`arm_node.py:146-149`（`destroy_node`）与 `:368-381`（`~/disable`）都会 `backend.disable()`。
而 SDK 自己的文档明确警告：撤掉力矩会让带重力负载的臂掉下来，仅在物理支撑时才可失能。

> 对比：`.onero_ws` 的桥接节点**刻意不自动 disable**，代码里写着理由：
> `# 不自动 disable：带载的机械臂突然卸力会掉落`（`topic_bridge.py:378`）。

---

### 🟡 S7｜运动学模型比 SDK 少 0.019 m

`a1_ros2_control.urdf.xacro:140` 的 joint1 origin 是 `xyz="0.0 0.0 0.0125"`，
SDK 权威 URDF 是 `0 0 0.0315`。子代理用 200 组随机构型做 FK 实测：
**位置系统性差 19.2 mm ± 0.4 mm**（固定 Z 偏置），姿态差 ≤0.0045°。

即：**MoveIt 的 FK/IK/TF 与 SDK 自身 FK 差 19 mm** —— 抓取会偏。

---

### 🟡 S8｜SRDF 缺 18 条碰撞排除 → **14% 状态被误判**

| 来源 | `disable_collisions` |
|---|---|
| SDK 权威 `onero_sdk/urdf/A1/a1_r.srdf` | **28 对** |
| `armsdk/ros2/config/a1.srdf` | **10 对**（只留了 7 条邻接 + 3 条） |
| `.onero_ws/config/onero_a1.srdf` | **28 对** ✅ 与 SDK 完全一致 |

**实测影响**（`tools/exp_srdf_ab.sh`，同一套 MoveIt 配置只换 SRDF，207 个采样状态）：

| SRDF | 无效状态 | 误判率 |
|---|---|---|
| `.onero_ws`（28 对） | 0 / 207 | **0.0%** |
| `armsdk/ros2`（10 对） | 29 / 207 | **14.0%** |

误判全部来自缺失的 `Link3 ↔ base_link`（SDK 里标注 `reason="Never"`）。
**后果：约 1/7 的合法位形被当成自碰撞，规划会莫名失败。**

---

### 🟡 S9｜`action_ns` 写法错误

`moveit_controllers.yaml:7` 写的是绝对路径 `/arm_controller/follow_joint_trajectory`。
MoveIt 的源码构造 action 名是 `name_ + "/" + namespace_` → 会拼成
`arm_controller//arm_controller/follow_joint_trajectory`，**永远连不上驱动**。

**官方约定是相对形式** —— 实测官方 panda 参考配置：

```
$ grep action_ns /opt/ros/jazzy/share/moveit_resources_panda_moveit_config/config/moveit_controllers.yaml
    action_ns: follow_joint_trajectory
```

`.onero_ws` 用的正是相对形式（且端到端已验证可用）。

---

### 🟡 S10｜重力补偿静默失效

`arm_node.py:70-78` 想启用 pinocchio 重力补偿，但调用的是
`_find_urdf("A1R")` —— 正确签名是 `_find_urdf("A1", "r")`，于是**永远返回 None**，
`if urdf_path:` 为假 → **连一行日志都不打**。（`model` 默认值若写成 `A1` 反而能走到。）

## 四、`.onero_ws` 的不足（要移植/修补的）

| # | 不足 | 说明 |
|---|---|---|
| W1 | **只支持 A1R** | 关节名硬编码 `jointN-a1_r`；SDK 的 A1L 限位是镜像的（`p_min=-3.14, p_max=1.04`），不能直接套 |
| W2 | **无重力补偿前馈** | 控制循环固定发 `torques=[0.0]*n`，而 `armsdk/ros2` 接了 pinocchio 重力矩 |
| W3 | **无 enable/disable 服务** | 只能靠 launch 参数；`armsdk/ros2` 有 `~/enable` `~/disable` |
| W4 | ~~IK 超时偏短~~ **（已实测推翻，见下）** | 原判：「`0.05` 偏短，应照 `armsdk/ros2` 改成 `0.2`」。**实测不支持这个结论**：`tools/exp_ik_timeout.py` 用 60 个由 FK 生成的可达位姿、零位形种子，四个超时值 0.02/0.05/0.1/0.2 的成功数**完全相同（36/60）**；且官方 `moveit_resources_panda_moveit_config` 用的也是 `0.05`。**结论：保持 0.05 不变。** |
| W5 | ~~`package.xml` 未声明话题桥插件~~ **（此条先前判断有误，已更正）** | 插件 `joint_state_topic_hardware_interface` **确实已声明**，位置在 `onero_a1_description`——正是使用它的 xacro 所在包，位置正确。见第九节的 rosdistro 审计实测结果 |
| W6 | 每周期多两跳 IPC | 话题桥固有代价，实时性弱于进程内方案 |

## 五、合并建议

### 5.1 总体：以 `.onero_ws` 为骨架

理由：它是唯一**跑通过**的一套，且覆盖了 `armsdk/ros2` 缺失的全部安全与工程能力（看门狗、NaN 防护、失联感知、无硬件验证、测试、文档、正确的参数装配）。

### 5.2 从 `armsdk/ros2` 移植这 3 样（它的真正价值点）

| # | 移植什么 | 怎么改 | 对应不足 |
|---|---|---|---|
| **1** | **重力补偿前馈** | `topic_bridge.py:296-302` 的 `torques=[0.0]*n` 换成 `DynamicsModel.gravity_torques(cmd)`，并加超时/异常降级 | W2 |
| **2** | **enable / disable 服务** | 在桥接节点上加 `std_srvs/Trigger`；`disable` 必须**要求物理支撑**并打警告 | W3 |
| **3** | ~~**IK 超时 0.2s**~~ **（实测否决）** | 原计划照 `armsdk/ros2` 把 `kinematics_solver_timeout` 从 0.05 改成 0.2。实测四个超时值成功率完全相同，且官方 panda 配置也是 0.05 → **不改**。详见 W4 | W4 |

> 注意第 1 项：`armsdk/ros2` 的实现里 `_find_urdf("A1R")` 是错的（S10），
> 移植时**不要把那个 bug 一起带过来**。

### 5.3 不要移植的东西

| 不要移植 | 原因 |
|---|---|
| `a1.srdf` | 缺 18 条碰撞排除 → 14% 状态误判（S8） |
| `a1_ros2_control.urdf.xacro` | 运动学差 19.2 mm（S7）+ 引用了不存在的插件（S13） |
| `move_group.launch.py` 的参数装配方式 | 两个致命阻断点（S1） |
| `moveit_controllers.yaml` 的 `action_ns` | 写法错误，永远连不上（S9） |
| `arm_node.py` 的轨迹执行逻辑 | 容差违规报成功（S2）、线程可静默死亡（S4）、安全层被绕过（S3） |

### 5.4 `armsdk/ros2` 该怎么处置

三个选项，建议 **B**：

| 选项 | 做法 | 评价 |
|---|---|---|
| A | 保留现状 | ❌ 留着会误导后来者（README 宣称"接口与 JTC 完全一致"，实测跑不起来） |
| **B** | **降级为参考实现**：README 顶部加显眼的现状说明（哪些能参考、哪些有已知缺陷、为什么改用话题桥），代码保留 | ✅ 保留历史决策记录，又不误导 |
| C | 删除 | ⚠️ 丢失"为什么不用 ros2_control"这段推理过程 |

### 5.5 建议补 W1（A1L 支持）

`.onero_ws` 目前硬编码 A1R。SDK 的 `model_registry` 已经支持 `A1L`（关节限位镜像）。
建议把关节名后缀和模型名参数化，`sync_*_from_sdk.py` 增加 `--variant l` —— 这是**做成产品**的必要条件。

## 六、交付物该放哪（需要你决策的战略问题）

现状是**分裂的**：

```
armsdk 仓库（公开、用户会看）        本地隐藏目录（用户看不到）
└── ros2/                             └── moveit2_ws/src/
    ├── onero_ros2/      ← 跑不通        ├── onero_a1_description/
    └── onero_moveit_config/            ├── onero_a1_bringup/
                                        └── onero_a1_moveit_config/  ← 能跑
```

上一轮会话的结论是「**被官方接纳 = rosdistro 发布**」（路径 B）。按那个结论：

1. **`moveit2_ws/src/` 的三个包应该迁到 `armsdk/ros2/`**（或独立仓库），改名对齐
2. `armsdk/ros2/onero_ros2` 要么降级为参考，要么删掉（见 5.4）
3. **工作区根目录现在采用标准 `src/<pkg>` 布局**，符合 bloom 对 `<ws>/src/<pkg>` 的要求
4. 包名建议保持 `onero_a1_*`，与 URDF 里的 `onero_a1` 前缀一致

> ⚠️ 这件事需要你先拍板，因为它决定后面所有打包工作的工作量。

## 八、证据复现方法

本次对比中用到的实验脚本都保留在 `tools/`，可随时复跑：

| 脚本 | 验证什么 | 输出 |
|---|---|---|
| `exp_srdf_ab.sh` | 两份 SRDF 的碰撞矩阵差异造成的**功能影响** | 207 采样状态的误判率对比 |
| `exp_srdf_validity.py` | 上面用的探针（调 `/check_state_validity`） | 无效状态数 + 触发的连杆对 |
| `exp_armsdk_stepwise.sh` | `armsdk/ros2` 的 launch **为何起不来**，分两步定位 | 两个独立阻断点的原始报错 |

```bash
cd /home/initialxx/project/moveit2_ws
bash tools/exp_srdf_ab.sh            # 碰撞矩阵 A/B（会临时替换 SRDF，结束自动恢复）
bash tools/exp_armsdk_stepwise.sh    # launch 阻断点定位（补丁打在副本上，不动原仓库）
```
